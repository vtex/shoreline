---
name: shoreline-create
description: Create or evolve Shoreline components, design tokens and themes using native contracts, contribution guidelines and deterministic validation. Use for implementation inside the design system, with or without an external design reference.
---

Read `tools/design-system/README.md`, `AGENTS.md`, the current private constitution/patterns and the relevant linked contribution guides. Preserve the user's authorized scope. A contract records decisions; it does not authorize publishing, merging, accepting visual snapshots or amending governance.

Use a schema-version-3 contract with `kind`, explicit target files/themes, semantic tokens and consumer impact. Create a draft with `pnpm ds init <kind> <id> --theme <name> --out <path>` when useful. Validate it and inspect its context before implementation. Native work has no source-repository requirement; if a pinned reference is present and a checkout supplied, verify it without executing copied source scripts. Record already established decisions without requesting approval again.

For **components**, start new families with `pnpm gen:component <Name> <theme>`. Existing components keep public barrels, React 18 `forwardRef`, Options/Props, JSDoc and accessible primitives. Use semantic data attributes and `--sl-*` tokens. Keep routing, transport, product stores and private cross-component imports outside library code. The generator defaults to Sunrise; explicitly select the intended theme. Shared JSX must not inject theme CSS. Add styles for each theme the new component promises to support.

For **tokens**, define the semantic reason and owning theme(s), inspect aliases and inherited values, then update theme CSS. Literal values belong in token definitions; component styles consume them. A new token can be added to Sunrise, Horizon or another theme as the design contract requires. Do not require byte identity with old Sunrise files. Ensure shared consumers receive a defined value or deliberate fallback in every supported theme. Run `pnpm ds tokens` or a scoped `--theme` check, followed by checks for all affected themes.

Run `pnpm ds tokens --components` to inspect all CSS, foundations and concrete JSX style references in every discovered theme. Runtime and shared component variables need a justified producer/consumer entry in `design-system/component-variables.json`, verified against actual source. A private variable defined in another file is not a global design token. Fix missing references at their owner; do not add arbitrary allowlists. Static analysis does not prove dynamic style values, DOM inheritance or computed-style semantics.

For **themes**, create CSS entries under `packages/shoreline/src/themes/<name>` and matching package exports. The shared registry discovers themes for build, scaffold, checks and visual tests. Reuse `src/foundations/reset.css` and `base.css` through imports; changes to shared behavior require all-theme validation. Keep palette and component inheritance explicit. Split inputs remain unlayered: public entrypoints/build own cascade layers. Full, tokens, reset, base and components entries have layered/unlayered forms. Run `pnpm ds themes` and verify emitted CSS with the bundler. A contract scaffold does not create source files.

Follow Storybook categories: Play for controls, Show for the agreed visual state matrix, Examples for usage and `stories/tests` for behavior. Only Show enables Chromatic snapshots. Components require meaningful unit coverage; tokens/themes use the evidence appropriate to their kind. Select one theme per preview document/build; global CSS from two themes in one document does not prove isolated coexistence.

Run `pnpm ds check --base <base> --lint`, token checks, package build/types and meaningful interaction tests. Then run `pnpm ds:visual:build` and `pnpm ds:visual:check`: every Show story must render across all discovered themes and viewports, with axe and reviewed screenshot baselines. Make interactive states visible in Show via deterministic setup/play; an image of a closed trigger does not validate an open overlay. Missing baselines fail. Use `ds:visual:capture` for diagnostic images; explicit `ds:visual:update` only creates candidates outside CI. Neither mode approves design. Never disable violations or skip themes to make a gate pass.

Read the runbook's limitations and CI gaps. Record artifacts with content hashes, the themes actually exercised and `pnpm ds fingerprint <contract>`; unavailable checks remain pending. Update consumer impact when implementation changes the contract. `pnpm ds contract <contract> --ready` verifies evidence integrity, not reviewer approval. Report executed checks and remaining review needs without equating a draft, scaffold or token foundation with a finished component.
